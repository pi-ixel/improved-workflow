# US Task Dev

基于 us-design-writer 生成的任务分解文档，逐个 task 进行开发实现。每次只处理一个 task，完成后输出任务总结并更新任务分解文档。

## Execution Discipline

`us-task-dev` 是串行任务执行技能。默认情况下，必须严格遵守以下规则：

- **锁定单一任务**：一旦确定当前任务编号，本轮只允许读取、修改、验证和总结该任务范围内的内容。不得在该任务完成前开始实现其他任务。
- **依赖优先**：只有当任务声明的所有依赖任务已完成（DoD 已勾选且总结非占位符）时，才能开始该任务。若用户指定的任务依赖未完成，停止实现并报告缺失依赖。
- **完成后再移动**：当前任务必须完成实现、DoD 验证、checklist 更新、总结写入后，才允许推荐或进入下一个任务。
- **编号顺序稳定**：自动选择任务时，按依赖满足后的编号顺序选择第一个未完成任务。不得因为任务看起来更简单、更相关或可并行而跳到后面的任务。
- **可并行仅作信息**：任务文档中的“可并行”字段只表示规划属性；在本技能的单 agent 执行中不得据此并行实现或提前切换任务。
- **连续执行也逐个提交**：若用户明确要求连续完成多个任务，也必须按“选择一个任务 -> 完成并更新文档 -> 重新读取任务状态 -> 选择下一个任务”的循环执行，不能交叉开发多个任务。

## Workflow

### 1. 定位任务分解文档

- 优先使用用户指定的文件路径。
- 若用户未指定，在当前工作目录下查找 `*-任务分解.md` 文件。若有多个匹配，列出供用户选择。
- 读取任务分解文档，提取所有任务信息：编号、标题、描述、依赖、DoD checklist、交付物、当前状态（是否有总结）。

### 2. 确定要开发的任务

两种模式，优先响应用户的显式指定：

**模式 A：用户指定任务编号**
- 用户说"实现 T1"、"开发 T3"等，直接定位对应任务。
- 检查该任务的依赖是否全部完成。依赖未完成时，不得开始实现该任务；报告阻塞它的任务编号和缺失状态。
- 若该任务已存在总结内容（已完成），提醒用户确认是否要重新开发。

**模式 B：自动推荐下一个任务**
- 从任务列表中找到满足以下条件的任务：
  - 尚未完成（描述中无"总结"内容或"总结"为模板占位符 `[完成后填写]`）。
  - 所有依赖任务均已完成（其总结不为空且不为占位符）。
- 若存在多个候选任务，按编号顺序选择并执行第一个。可以在最终报告中提及其他可执行任务，但不得在当前任务完成前处理它们。
- 若无可执行任务（全部完成或依赖未满足），告知用户当前状态，列出阻塞原因。

### 3. 收集开发上下文

确定任务后，读取以下材料：

- **设计文档**：任务分解文档头部标注的来源设计文档路径。读取完整的 US 设计文档，理解整体方案和接口设计。
- **项目结构**：浏览项目的目录结构，了解代码组织方式。若项目中存在 `software_architecture.md`，读取该文件理解模块边界。
- **相关代码**：根据设计文档中标注的变更文件和影响范围，读取当前代码现状。如果涉及接口调用或依赖，也读取相关文件。
- **依赖任务产出**：若该任务依赖其他任务，读取已完成任务的相关代码或产出，理解接口契约。

将收集到的上下文整理为开发要点摘要。若不存在会改变实现方向的存疑点，直接进入开发阶段；只有当前任务存在阻塞性歧义时才向用户提问。

### 4. 实现任务

根据设计文档和任务描述，实现代码。

- 按照任务描述和设计文档中的接口规范、数据结构、错误码等定义进行实现。
- 严格遵循项目中已有的代码风格和命名约定。
- 当前任务未完成前，不得顺手实现后续任务的功能。若发现后续任务需要的前置改动，记录到当前任务总结或最终报告中，不提前开发。
- 如果设计文档中标记了 `【存疑】` 的内容恰好影响当前任务实现，不要猜测——向用户提问确认后再继续。
- 如果实现过程中发现设计与实际情况有冲突（如接口签名不匹配、依赖模块行为不同），暂停并向用户报告，由用户决定是否调整设计或实现方式。

### 5. DoD 验证

根据任务的 DoD checklist 逐项验证：

- **功能项**：确认每个功能验收点的代码实现符合描述。
- **测试项**：按 DoD 中描述的测试要求运行或编写测试。如果 DoD 要求具体的测试覆盖率或测试场景，执行并确认通过。
- **文档项**：确认需要更新的文档已完成。

验证过程中：
- 通过的项目，在任务文档中勾选对应 checklist（将 `[ ]` 改为 `[x]`）。
- 未通过的项目，修复后重新验证。如果无法修复（如环境问题、依赖缺失），在总结中标注。

### 6. 输出任务总结

在任务分解文档中对应任务的 `**总结：**` 字段写入任务总结。总结格式如下：

```markdown
**总结：**
## 变更摘要
- 修改文件：[列出所有新建和修改的文件]
- 核心实现：[1-3 句话描述核心逻辑]
- 关键决策：[如有偏离设计文档的决策，说明原因]

## 遇到的问题
- [问题1：描述 + 解决方式]
- [问题2：描述 + 解决方式]
（如无问题，写"无"）
```

总结要简洁、聚焦于对后续任务有参考价值的信息。不要写流水账，只写影响代码质量和后续开发的关键信息。

### 7. 更新任务分解文档

将更新后的任务分解文档写回原文件。更新内容包括：
- DoD checklist 勾选状态。
- 任务总结内容。

更新完成后，向用户报告：
- 完成的任务编号和标题。
- DoD 通过情况（全部通过 / 部分通过及原因）。
- 下一个可执行的任务（如果有的话）。

## Quality Gates

实现完成、输出总结前，逐项自检：

- 本轮只实现了锁定的当前任务，没有提前实现其他任务。
- 当前任务所有依赖已完成；若用户指定了依赖未满足的任务，本轮未进行实现。
- 任务实现与设计文档描述一致（如有偏离，已在总结中说明原因）。
- DoD checklist 中的每一项都已执行，结果已记录。
- 代码遵循项目现有风格和约定。
- 没有遗留 `【存疑】` 相关的猜测性实现。
- 任务总结包含变更摘要和遇到的问题。
- 任务分解文档已更新（checklist + 总结）。

## Output Rules

- 代码输出遵循项目现有代码风格。
- 任务总结使用 Markdown，写入任务分解文档对应位置。
- 任务分解文档更新后写回原文件路径。
- 如果用户要求仅在对话中展示总结，则不更新文件。
- 最终报告只推荐下一个可执行任务，不自动开始下一个任务，除非用户明确要求连续执行。
- 使用简洁、工程化语言。

## Template Contract

- 读取任务分解文档格式遵循 us-design-writer 的 `references/任务分解.md` 模板结构。
- 任务总结写入模板中的 `**总结：**` 字段。
- DoD checklist 更新格式：`[ ]` → `[x]`。

## Quick Start Prompt

`使用 $us-task-dev，读取任务分解文档 ./<变更描述>-任务分解.md，实现 T1 任务，按 DoD checklist 验证，完成后输出任务总结并更新文档。`
