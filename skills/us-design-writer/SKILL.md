# US Design Writer

基于需求材料输出可开发落地的详细设计文档，经用户审批确认后，进一步拆分为可独立验收的任务分解文件。严格遵循 skill 内置模板。

## Workflow

### Phase 1: 设计文档生成

1. 定位模板文件（固定来源）。
- 默认模板路径：`<skill-dir>/references/us设计.md`。
- 除非用户明确指定其他模板路径，否则不得改用项目根目录模板。
- 若内置模板缺失，明确报错并要求先补齐该文件。

2. 收集输入材料。
- 读取用户提供的所有材料：需求描述、PRD、历史设计文档、接口文档、代码现状、测试基线。
- 如果用户未提供具体材料，主动询问关键信息：目标、范围、受影响模块、接口约束、非功能指标。
- 将收集到的事实整理为结构化摘要，在开始写作前向用户确认理解是否正确。

3. 按模板逐段填充内容。
- 保持模板一级/二级标题不变。
- 以下章节的写作要点：

  **WHY** — 只写背景与现状（1-2句话），不写方案细节。读者看到 WHY 后应该理解"为什么要做这件事"而不是"怎么做"。

  **核心机制** — 必须包含 mermaid 图。先画流程图表达主路径，再补充异常分支。mermaid 图要让不熟悉项目的人也能看懂数据流向和处理逻辑。

  **实现细节** — 每个接口必须包含：接口原型（函数签名或 API 定义）、返回值语义（每个返回值的含义）、错误码（命名 + 含义）。非功能约束要写具体数值而非模糊描述（如 "P99 < 200ms" 而非 "尽量快"）。

  **验证和测试** — 要覆盖五类场景：正常流程、异常流程（错误输入、依赖失败）、边界条件（空值、溢出、并发）、性能指标（量化标准）、可观测性（日志、指标、告警）。不要只写"测试通过"，要写具体的验证点和验收标准。

  **风险与回滚** — 每个风险项必须包含三要素：风险描述 + 触发条件 + 缓解措施。回滚策略要可操作（具体开关、步骤）。

4. 处理不确定信息。
- 禁止猜测。宁可多标记存疑，也不要用看似确定但实际未验证的信息。
- 无法确认的信息标记 `【存疑】`。
- 在对应段落追加 `待确认问题：...`，问题要具体到可以让负责人直接回答（如 "DB 索引是否已覆盖 user_id + status 组合查询？" 而非 "查询性能是否OK？"）。
- 在文末 `存疑汇总（Open Questions）` 表中登记每个存疑项。
- 设计文档生成后、进入审批节点前，若存在存疑项，主动向用户逐项询问待确认问题，将用户的回答补充到文档中并消除对应存疑标记。如果用户暂时无法回答，保留存疑标记，继续流程。

5. 输出设计文档。
- 默认输出到以需求ID命名的目录：`./<需求ID>/<变更描述>-us设计.md`。
  - 需求ID由用户提供；若用户未提供，主动询问。
  - 若目录不存在，先创建目录再写入文件。
- 若用户明确要求仅在对话展示，则不写文件，仅输出 Markdown 正文。

### 审批节点

6. 设计文档生成后，询问用户：
   - **确认** → 进入 Phase 2。
   - **需要修改** → 用户提出修改意见，修改后重新询问确认（支持多轮）。
   - **中止** → 流程结束，不进入 Phase 2。

7. 多轮修改时：
- 根据用户意见修改设计文档并重新写入。
- 每轮修改完成后重新询问确认。
- 仅在用户明确确认后才进入 Phase 2。

### Phase 2: 任务分解

8. 定位任务分解模板（固定来源）。
- 默认模板路径：`<skill-dir>/references/任务分解.md`。
- 若内置模板缺失，明确报错并要求先补齐该文件。

9. 读取确认后的设计文档，执行任务拆分决策。
- 读取 Phase 1 输出的最终版设计文档。
- 对设计文档中的每个实现点进行分类，然后按决策树拆分任务。

**第一步：分类 — 区分业务实现与通用工具**

逐项审视设计文档中的每个实现点，判定其属于哪一类：
- **业务实现**：特定业务场景的逻辑，如订单处理、用户注册、权限校验等。判断依据——如果这段代码只为当前需求服务，不具备跨需求复用价值，就是业务实现。
- **通用工具/基础设施**：可被多个业务场景复用的代码，如工具函数、公共数据结构、通用中间件、基础配置等。判断依据——如果剥离当前需求后，其他功能也可能使用，就是通用工具。

将分类结果记录在每个任务的描述中，格式：`类型：业务实现` 或 `类型：通用工具`。

**第二步：按决策树拆分任务**

```
对每个实现点，按以下决策树判断拆分方式：

1. 是否为通用工具？
   ├─ 是 → 拆分为 1 个独立任务（无论代码量大小）
   └─ 否（业务实现）→ 进入步骤 2

2. 是否跨模块？
   │  检查方式：优先读取项目中的 software_architecture.md 确认模块边界；
   │  若该文件不存在，则根据设计文档中的功能划分和代码目录结构判断。
   ├─ 是（跨模块）→ 进入步骤 3
   └─ 否（单模块）→ 进入步骤 4

3. 跨模块 + 可独立验证？
   ├─ 是 → 按模块拆分为独立任务，每个任务对应一个模块的变更
   └─ 否（模块间强耦合）→ 合并为 1 个任务，在描述中标注跨模块耦合原因

4. 单模块，预估代码量？
   ├─ ≤ 400 行 → 合并为 1 个任务
   └─ > 400 行 → 拆分为多个子任务，每个子任务 ≤ 400 行
```

**第三步：独立可验证性校验**

拆分完成后，对每个任务进行最终校验：
- 每个任务必须有明确的验收标准，能独立部署和验证，不依赖其他未完成任务的运行时状态。
- 400 行是硬限制——任何任务不得超过 400 行，除非拆分会破坏独立可验证性（此时在任务描述中说明原因）。
- 依赖关系仅限于数据结构定义或接口契约，不应该是"我的业务逻辑写在你里面"这种运行时耦合。

10. 按任务分解模板填充内容。
- 每个任务为里程碑级，包含编号（T1, T2, ...）、描述、依赖关系。
- 每个任务包含 DoD checklist（功能/测试/文档三类）和交付物。
- DoD 要具体可验证：写"新增接口 A 的单元测试，覆盖率 > 80%"而不是"完成测试"。
- 顺序通过编号表达，依赖通过 `依赖: T1, T2` 字段声明。
- 可并行的任务不标注相互依赖。

11. 处理不确定信息（同 Phase 1 规则）。
- 禁止猜测，标记 `【存疑】`，在文末汇总表中登记。

12. 输出任务分解文件。
- 默认输出到以需求ID命名的目录（与设计文档同目录）：`./<需求ID>/<变更描述>-任务分解.md`。
- 文件头部标注来源设计文档路径，便于追溯。

## Quality Gates

生成结果前，逐项自检：

**Phase 1 自检（设计文档）：**
- 模板全部一级章节均已填写，无遗漏。
- `实现方案/核心机制` 含至少 1 个 mermaid 图。
- 所有接口均有原型与返回值语义。
- 至少包含 1 个异常场景和 1 个性能指标（如适用）。
- 所有 `【存疑】` 均在文末汇总表中有对应记录。
- 风险项均包含三要素（描述 + 触发条件 + 缓解措施）。

**Phase 2 自检（任务分解）：**
- 每个任务包含编号（T1, T2, ...）、标题和类型标注（业务实现/通用工具）。
- 任务拆分符合决策树逻辑：通用工具独立一个任务；跨模块业务按模块拆分；单模块业务按 400 行拆分。
- 每个任务包含 DoD checklist（功能/测试/文档三类），且每项具体可验证。
- 每个任务可独立验证——验收标准不依赖其他未完成任务的运行时结果。
- 每个任务预估代码量 ≤ 400 行，超出的必须说明原因。
- 每个任务包含交付物列表。
- 依赖关系已明确声明，串行/并行关系清晰。
- 所有 `【存疑】` 均在文末汇总表中有对应记录。

## Output Rules

- 输出使用 Markdown。
- 除非用户要求，不改写模板标题文案。
- 使用简洁、工程化语言，避免空话。
- 优先给出可落地信息：接口、数据、边界、回滚、验收证据。
- Phase 2 输出文件头部必须包含来源设计文档路径。

## Template Contract

- 两阶段分别遵循对应模板约束：
  - Phase 1：`references/us设计.md`
  - Phase 2：`references/任务分解.md`
- `重要：在写作过程中出现存疑，或者无法通过上下文进行决定，不能做出任何猜测，需要标记为存疑，并抛出问题`
- 若模板与用户额外要求冲突，以用户明确要求为准，并在文档中标注偏差点。
